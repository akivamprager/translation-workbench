# Translation workbench

The user translates texts page by page with Claude. Claude drafts the translation; the user
reviews and edits it in a local web app (`server.py`, http://localhost:8765) that shows the
source and the translation side by side. **The app is where translations live — do not paste
full translations into the chat.** The chat is for short reports and questions.

Each text is a *project* in `projects/<name>/`. All commands act on the **active project**
(`python3 tools/tm.py projects` shows it; `tm.py use NAME` switches). See README.md for the layout.

## Project files (get exact paths with `tm.py paths`)
- `style-guide.md` — the user's translation instructions for this project. **Follow it exactly.**
- `decisions.md` — living glossary + style decisions. Read before every page. Append new decisions/lessons here.
- `project.json` — title, languages, sections, input settings.
- `source.json` — source text split into blocks (heading / epigraph / para / quote), grouped by page, with footnotes. Generated by `tm.py import`; don't edit by hand.
- `translation.json` — translation per block, status, history, alternatives. **Never edit directly — always use `tools/tm.py`.**
- `requests.json` — requests the user made from the app. `edits.jsonl` — log of the user's manual edits.
- `pages/pN.png` — page images, when the input is a PDF (Read one when italics/layout matter).

## Commands (python3 tools/tm.py …)
`projects` · `use NAME` · `new NAME --pdf|--text FILE` · `import` · `paths` · `status` · `next` · `show N` · `put FILE.json` · `alt FILE.json` · `requests` · `resolve ID` · `edits [--mark]` · `export`

## Workflow: "תרגם עמוד N" / "עמוד הבא" / "next page"
1. `tm.py edits` — if there are unseen manual edits, study how the user changed Claude's drafts. Turn any generalizable lesson into a line in `decisions.md` (term choices, register, phrasing habits), then `tm.py edits --mark`. Mention briefly what you learned.
2. Read `decisions.md` (and `style-guide.md` if not already in context this session).
3. `tm.py show N` (N from the user, or `tm.py next`). It prints the source blocks, footnote texts, and the preceding translation for continuity.
4. Translate every block on the page per the style guide: draft, then a second polishing pass. A block marked "continues onto next page" is translated whole. Footnotes: follow `decisions.md` (by default keep only notes that explain a term or the method; drop the rest *and* their markers). Kept notes: marker `[^n]` in the translation, the translated note in the page notes.
5. Write the JSON to the project's inbox — `projects/<name>/.inbox/pN.json` (git-ignored; `tm.py paths` shows it) — and run `tm.py put <that file>`; tm.py deletes inbox files after importing them. JSON: `{"page": N, "blocks": {"pN-1": "…", …}, "notes": "…"}` — `notes` holds hesitations, short and few, in the target language; omit if none. `put` refuses to overwrite blocks the user approved or edited (only use `--force` if the user asked).
6. Reply in 1–3 lines: page done, how many blocks, any hesitation worth a look. The app refreshes by itself.

The user can also say "תרגם עמודים 5–7" — do them in order, one `put` per page.

## Workflow: "טפל בבקשות" (requests from the app)
`tm.py requests` lists them.
- `alternatives`: the user selected a phrase. Following the style guide's rule for rephrasing requests, propose **at least 3** alternatives that fit the sentence and whole text. Write them to the inbox and run `tm.py alt <file>`, where the JSON is `[{"block": id, "target": "<exact selected text>", "why": "<short>", "options": [{"text": "<replacement for target>", "note": "<pros/cons, short>"}], "request": ID}]`. `target` must be an exact substring of the current translation so the app can swap it in on click; each option is a drop-in replacement for exactly that substring.
- `retranslate`: retranslate the whole block taking the user's comment into account; write with `put` (add `--force` if the block was user-edited/approved — the user asked for it), then `tm.py resolve ID`.
Report in a line or two.

## Global changes
When the user approves a global decision (e.g. "אבל"→"אך" everywhere), record it in `decisions.md`, then apply it to existing blocks with `put --force` — list which blocks you changed, and never silently change text the user edited by hand without saying so.

## Setting up a new project ("I want to translate X")
1. `tm.py new NAME --pdf FILE` or `--text FILE` (`--title`, `--from en`, `--to he`). Text/Markdown imports immediately (format in `tools/import_text.py`).
2. PDF: inspect it (`pdftotext -layout -f P -l P FILE -` for a few pages, find where the wanted parts start, the page-number offset, running headers, paragraph/quote indents, headings, endnote pages). Fill `project.json` → `sections` and `input` (options documented at the top of `tools/extract_pdf.py`), run `tm.py import`, then check `tm.py show N` on several pages — paragraph splits, quotes, footnote markers, hyphenation — and iterate until clean. Changing the config after translation has started can change block ids; avoid that once work has begun.
3. Ask the user for their style guide (or keep the template copied into the project) and any known decisions; put them in `style-guide.md` / `decisions.md`.
4. `tm.py use NAME`; the app switches automatically.

## Other
- Technical questions (names, facts) — answer normally; the style guide's output rules don't apply.
- Export: the app's "ייצוא" button downloads the translation as plain text; `tm.py export` writes `<project>/output/translation.txt`.
- Start the app: preview_start with the "workbench" config (`.claude/launch.json`), or `python3 server.py [NAME]`.
- `projects/*` is git-ignored except `projects/example` — source texts and translations stay local.
